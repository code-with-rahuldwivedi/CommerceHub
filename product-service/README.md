# ShopSphere – Product Service

A production-oriented product catalog microservice built using **Spring Boot 3.5, Java 17, MySQL, and Flyway**.

The service manages product creation, catalog search, filtering, pagination, product lifecycle, and administrative operations.

Access tokens are issued by **user-service** and verified using RS256 signatures against its JWKS endpoint.

## 2. API Endpoints

### 2.1 Public Product APIs

| Method | Endpoint | Access | Description |
|---|---|---|---|
| GET | `/api/products` | Public | Search, filter, sort and paginate products |
| GET | `/api/products/{id}` | Public | Retrieve a product by ID |
| GET | `/api/products/batch?ids=1,2,3` | Public | Retrieve up to 100 ACTIVE products |

**Catalog visibility rules:**
- Anonymous users and customers can only see ACTIVE products.
- Administrators can also view INACTIVE and ARCHIVED products.
- Unpublished products return 404 to customers, not 403.

### 2.2 Admin Product APIs

All endpoints require the `ADMIN` role.

| Method | Endpoint | Description |
|---|---|---|
| POST | `/api/products` | Create a product (201 Created + Location header) |
| PUT | `/api/products/{id}` | Update an existing product |
| PUT | `/api/products/{id}/status` | Change product status |
| DELETE | `/api/products/{id}` | Soft-delete (archive) a product |

**Product status operations:**

- `ACTIVE` – Publish a product.
- `INACTIVE` – Unpublish a product.
- `ARCHIVED` – Archive a product.
- Changing an archived product's status can restore it.

### 2.3 Deprecated Legacy APIs

These endpoints are retained for backward compatibility with existing clients and gateway routes.

| Method | Endpoint | Description |
|---|---|---|
| POST | `/api/createProduct` | Legacy product creation |
| GET | `/api/getAllProducts` | Retrieve up to 500 products |
| GET | `/api/product/{id}` | Retrieve product |
| PUT | `/api/product/{id}` | Update product |
| DELETE | `/api/product/{id}` | Delete/archive product |

Responses include:

`Deprecation: true`

**Note:** Remove `LegacyProductController` once no existing clients depend on these endpoints.

## 3. Product Search, Filtering and Pagination

Endpoint:

`GET /api/products`

| Parameter | Description |
|---|---|
| `q` | Case-insensitive product name search |
| `category` | Filter by product category |
| `minPrice` | Minimum product price |
| `maxPrice` | Maximum product price |
| `status` | Filter by status (ADMIN only) |
| `page` | Page number (minimum 0) |
| `size` | Page size (1–100, default 20) |
| `sort` | Sorting field and direction |

**Supported sorting fields:**

- `id`
- `name`
- `price`
- `createdAt`
- `updatedAt`

Examples:

```http
GET /api/products?q=iphone
GET /api/products?category=ELECTRONICS
GET /api/products?minPrice=1000&maxPrice=50000
GET /api/products?page=0&size=20
GET /api/products?sort=price,asc
GET /api/products?sort=createdAt,desc
```

Default sorting:

`createdAt,desc`

Unsupported sorting fields return HTTP 400 Bad Request.

### Response Structure

```json
{
  "content": [
    {
      "id": 1,
      "name": "iPhone 17",
      "price": 89999.00,
      "category": "ELECTRONICS",
      "status": "ACTIVE"
    }
  ],
  "page": {
    "size": 20,
    "number": 0,
    "totalElements": 1,
    "totalPages": 1
  }
}
```

## 5. Authentication and Authorization

The product-service does not issue access tokens. It verifies tokens generated by user-service.

### JWT Verification Flow

1. Client sends an access token in the Authorization header.
2. Product-service extracts the JWT.
3. JWT algorithm is restricted to RS256.
4. Signature is verified using the user-service JWKS endpoint.
5. Public key is selected using the JWT `kid` header.
6. Unknown `kid` triggers JWKS refresh to support key rotation.
7. Token claims are validated.
8. Authentication and authorization are established.

### JWT Claims Validation

| Claim | Validation |
|---|---|
| `alg` | RS256 only |
| `kid` | Key identifier |
| `exp` | Token expiration |
| `iss` | JWT issuer |
| `aud` | JWT audience |
| `sub` | Numeric user ID |
| `role` | USER or ADMIN |

Role mapping:

| JWT Role | Spring Security Authority |
|---|---|
| USER | ROLE_USER |
| ADMIN | ROLE_ADMIN |

### JWKS Configuration

- JWT public keys are retrieved from user-service.
- Unknown key identifiers trigger JWKS refresh.
- JWKS connection timeout: 2 seconds.
- JWKS read timeout: 3 seconds.
- User-service downtime does not prevent product-service startup.
- Requests containing tokens fail authentication when verification cannot be completed.
- Anonymous catalog reads remain available.

**Token validity:** A role change or disabled user takes effect when the existing 15-minute access token expires or is refreshed.

## 6. Catalog Business Rules

### Product Lifecycle

Products are never physically deleted because existing orders may reference their product IDs.

Instead, deletion archives the product.

### Product Update Rules

- Editing an archived product returns HTTP 409 Conflict.
- Archived products must be restored before editing.
- Administrators can update products using the latest version.
- Stale versions return HTTP 409 Conflict.

### Optimistic Locking

The client sends the last-read `version` during product updates.

Example:

```json
{
  "name": "iPhone 17 Pro",
  "price": 129999.00,
  "version": 2
}
```

If another administrator updates the product first, the stale update is rejected with HTTP 409.

Without a version, updates follow last-write-wins behavior.

### Soft Delete

- DELETE changes product status to ARCHIVED.
- Repeated delete operations are idempotent.
- Successful deletion returns HTTP 204 No Content.

## 8. Exception Handling

All API errors follow the RFC 9457 Problem Details format.

Content type:

`application/problem+json`

### Common HTTP Responses

| HTTP Status | Description |
|---|---|
| 400 | Bad Request / Validation Failure |
| 401 | Unauthorized |
| 403 | Forbidden |
| 404 | Product Not Found |
| 409 | Conflict / Concurrent Update |
| 500 | Internal Server Error |

Validation errors include an additional `errors` map containing field-specific messages.

Every response includes:

`X-Request-Id`

## 9. Database and Flyway Migrations

Database: MySQL

Flyway migrations:

- V1 – Initial database schema.
- V2 – Product lifecycle and additional database constraints.

### V2 Changes

- Added `status`.
- Added `version`.
- Added `created_by`.
- Added `updated_by`.
- Added UTC-safe timestamp defaults.
- Added `CHECK (price > 0)` constraint.
- Added search indexes.

### Existing Database Migration

If the database already contains a `products` table but does not contain `flyway_schema_history`, perform the initial baseline using:

```bash
SPRING_FLYWAY_BASELINE_ON_MIGRATE=true
SPRING_FLYWAY_BASELINE_VERSION=1
```

After successful migration, remove both temporary settings.

### Search Performance

Product name search currently uses:

```sql
LIKE '%text%'
```

This is not index-assisted.

For catalogs with hundreds of thousands of records, consider:
- MySQL FULLTEXT indexing.
- A dedicated search engine.

| Endpoint | Purpose |
|---|---|

- `/actuator/health/**` is public.

## 12. Testing Strategy

The project uses multiple testing approaches.

| Testing Type | Technology | Purpose |
|---|---|---|
| Unit Testing | JUnit 5, Mockito | Business logic |
| API Testing | MockMvc | Controller and HTTP behavior |
| Integration Testing | Spring Boot Test | Application integration |
| Database Testing | H2 | Fast database tests |
| MySQL Integration | Testcontainers | Real MySQL behavior |
| Security Testing | Embedded JWKS server | JWT verification |
| Coverage | JaCoCo | Code and branch coverage |

### Running Tests

Run all verification checks:

```bash
mvn verify
```

This executes:

- Unit tests.
- MockMvc tests using H2.
- JWKS/JWT integration tests.
- MySQL Testcontainers tests.
- Coverage gate.

MySQL integration tests require Docker and are skipped automatically when Docker is unavailable.

Tests use an embedded JWKS server and generate signed tokens compatible with user-service, exercising the actual security chain.

### Generate JaCoCo Report

```bash
mvn clean test jacoco:report
```

Report location:

```text
target/site/jacoco/index.html
```
